# Plus plan (S$4.99, 5,000 credits/day) + Pro daily replenishment

## Goal

Add a **Plus** subscription tier at **S$4.99 SGD / month** that grants **5,000 credits per day** and nothing else, and convert **Nova Pro** from a 10,000-credit monthly pool into a **10,000-credit daily allowance** (both reset at UTC midnight).

## Current context / assumptions

**Tier ladder after this change** (all daily, UTC reset via `getCreditDay()`):

| Tier | Price | Credits | Premium models | Agents/teams |
|---|---|---|---|---|
| Free | S$0 | 500 / day | no | no |
| **Plus (new)** | **S$4.99 / month** | **5,000 / day** | **no** | **no** |
| Pro | S$7.99 / month | 10,000 / day | yes | yes |

Confirmed with the user: Pro's 10,000-credit **monthly pool is replaced** by a 10,000-credit **daily** allowance.

**What exists today** (all paths relative to `~/nova-cloud-computer`):

- `server/credits.ts` — policy constants and pure helpers. `PlanTier = "free" | "paid"`. `DEFAULT_DAILY_CREDITS = 500`, `ADMIN_DAILY_CREDITS = 1000`, `PAID_PLAN_MONTHLY_CREDITS = 10_000`, `PAID_PLAN_CARRY_OVER_MONTHS = 12`, `PAID_PLAN_PRICE_CENTS = 799`. Daily policy is **role-based**: `getDailyCreditPolicyForRole(role, region)`.
- `server/db/credits.ts` — `getSubscriptionForUser()` maps the `user_subscriptions` row to `plan: "paid" | "free"` (only `row.plan === "paid"` and an active status count). `claimDailyCreditForUser()` and `getDailyCreditStatusForUser()` both call `getDailyCreditPolicyForRole`. The monthly pool lives in `monthlyCredits` table + `claimMonthlyCreditForUser` / `settleMonthlyCreditUsageForUser` / `ensureMonthlyAllocationForUser` / `getMonthlyCreditStatusForUser`.
- `server/aiGateway.ts` — `claimDailyCreditOrThrow()` branches on `isPaidPlanForUser()`: paid → monthly pool → purchased bundle → error; free → daily → purchased → error. `CreditFundingSource = "daily" | "monthly" | "purchased"`.
- `server/whop.ts` — `getWhopPlanId()` reads `WHOP_PLAN_ID`; `getWhopPriorityPlanId()` reads `WHOP_PRIORITY_PLAN_ID`. `membershipToState()` hardcodes `plan: active ? "paid" : "free"`. The webhook **ignores** any membership whose plan id is not the pinned Pro plan (`ignored-non-pro-membership`).
- `server/routers.ts` — `billing.createCheckout` (Pro only), `billing.subscription` (returns `monthlyCredits`, `creditTopUps`, `proAccess`, `accessActive`, `trialEndsAt`, `plan`, …).
- `client/src/pages/Checkout.tsx` — `Product = "pro" | "priority"`, driven by `?product=`.
- `client/src/pages/Billing.tsx` — three `PlanCard`s (Free / Pro / Priority) + a credits card that reads `subscription.data.monthlyCredits`.
- `client/src/components/DashboardLayout.tsx` — `ACCOUNT_PLANS` + exported `planRows(proAccess, isAdmin)`; the account menu shows the current tier.
- `client/src/i18n/en.ts` + 16 locale files; locales are machine-generated by `pnpm run i18n:translate` and type-checked against `Translations`, so **any new key must be translated before `pnpm run check` passes**.

**Assumptions (state these in the PR):**

1. `user_subscriptions.plan` is `varchar(24)` — `"plus"` needs **no schema migration**.
2. Plus is a recurring monthly subscription, mutually exclusive with Pro (one subscription row per account, unique on `ownerId`).
3. Plus does **not** unlock premium models, agents, or teams — only the daily allowance.
4. Admins keep their elevated role allowance (`max(ADMIN_DAILY_CREDITS, plan allowance)`); developers stay unlimited.
5. The `monthly_credits` table is left in place but becomes unused (no drop migration).
6. Existing Pro subscribers' unused pooled balance is forfeited — the daily allowance is strictly more generous.

## Architecture / proposed approach

Keep one ledger (`daily_credits`) and make the **allowance plan-aware**: `getSubscriptionForUser()` learns to return `"plus"`, `getDailyCreditPolicyForAccount(role, plan)` replaces the role-only policy, and `claimDailyCreditForUser()` reads the plan before claiming. Pro then needs no special funding path, so `claimDailyCreditOrThrow()` collapses to *daily → purchased → error* and the whole monthly-pool machinery is deleted. On the billing side, `createCheckout` takes a `plan` param, the Whop webhook maps a pinned Plus plan id to the `"plus"` tier, and the client gains a Plus plan card + `?product=plus` checkout.

export function getDailyCreditPolicyForPlan(plan: PlanTier) {

  return DEFAULT_DAILY_CREDITS;

/**
 * Daily credit policy for an account: the plan sets the allowance and the role
 * only elevates it (admins get at least ADMIN_DAILY_CREDITS, developers are
 * unlimited).
 */
export function getDailyCreditPolicyForAccount(role: CreditRole, plan: PlanTier, region = DEFAULT_CREDIT_REGION) {
  const base = getDailyCreditPolicy(region);
  if (role === "developer") return { region: base.region, dailyCredits: null, unlimited: true } as const;
  const planDaily = getDailyCreditPolicyForPlan(plan);
  if (role === "admin") return { region: base.region, dailyCredits: Math.max(ADMIN_DAILY_CREDITS, planDaily), unlimited: false } as const;
  return { region: base.region, dailyCredits: planDaily, unlimited: false } as const;
}

## Risks, tradeoffs, and open questions

1. **Existing Pro subscribers lose their rolled-over pool.** `monthly_credits` rows become orphaned. The daily allowance is more generous (10,000/day vs 10,000/month), so no user is worse off — but if finance needs the old balance honoured, add a one-off migration before Task 2 ships. **Decision needed.**
2. **`monthly_credits` table is left behind.** Dropping it would need a migration and would destroy the audit trail of past allocations. Recommendation: leave it, document it as retired.
3. **Plus checkout without `WHOP_PLUS_PLAN_ID`.** The inline-variant fallback creates a new S$4.99 variant per purchase (no Apple Pay, no pinned price). Task 0 must land before Plus is advertised.
4. **Plan elevation takes effect the same day.** `claimDailyCreditForUser` refreshes `allocatedCredits` on every claim, so upgrading mid-day raises today's cap — but `usedCredits` already spent stays spent (no refund). Downgrading mid-day lowers the cap immediately, which can strand a user who spent above the new cap until UTC midnight. Acceptable, but worth a line in the changelog.
5. **`getDailyCreditStatusForUser` now returns the policy value, not the row's.** A stale row (created before an upgrade, no claim yet today) shows the new allowance while `usedCredits` is 0 — correct, and the first claim reconciles the row.
6. **i18n translation latency.** `pnpm run i18n:translate` hits rate limits; run it in the background and verify every locale before `pnpm run check`.
7. **Open question:** should Plus subscribers be allowed to buy Pro later without a proration path? Today the checkout is a flat S$7.99 switch (Whop handles the upgrade); the conflict check only blocks buying the tier you already hold. No proration logic is planned.
